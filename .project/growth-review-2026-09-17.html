Summary

The foundation is complete as a skeleton and empty as a product. It has a control plane, two runtimes, three packages, and a thorough policy file, but not one feature directory, not one business route, and no example of the feature-first model it prescribes. The rules for <feature>.route.ts, <feature>.service.ts, and domain/ are written down and enforced, yet nothing in the tree demonstrates them.

The largest gap is therefore not a missing tool. It is the missing reference feature that proves the conventions end to end: a shared schema, a server feature, a typed client, a web feature, persistence, auth, and tests at each level. The planned M03.3 auth slice is the right vehicle. Most recommendations below either prepare for that slice or are triggered by it.

Structure

The physical layout is clean and the plane separation is real. The gaps are places where a convention is prescribed but has no physical home yet, and places where one-off tooling is appearing outside the control plane.

NowSTR-1

Give server features a physical root and a registration contract

architecture.yaml featureModel · servers/api/bootstrap/create-app.ts

The policy names featureRoot: "features" for UI but never says where server features live, and create-app.ts registers /health inline. Declare servers/<runtime>/features/<feature>/ in policy, and have each feature export a router factory that receives explicit dependencies. The composition root then becomes a list, and health becomes the first feature that follows the rule.

// servers/api/features/health/health.route.ts
export const createHealthRoutes = ({ config, database }: HealthDependencies) => router;

// bootstrap/create-app.ts
const features = [createHealthRoutes(deps), createAuthRoutes(deps)];
features.forEach((routes) => app.use("/v1", routes));
NowSTR-2

Extract shared tooling configuration into config packages

packages/tsconfig · packages/eslint-config

Five ESLint configs and four tsconfigs repeat the same strict flags. Config-only packages are the one place where extraction is justified before feature reuse, because the reuse is already real. The control plane's tsconfig policy check can then verify extends instead of re-reading twelve flags per unit. Decide whether these need a new project type such as config, since they have no build, lint, or test task.

NowSTR-3

Bring package-local scripts under the control plane or document them

packages/ui/scripts/reconcile-registry.mjs

A registry reconciliation script has appeared inside the UI package. Repository-wide policy reconciliation is control-plane work by the repo's own definition. Either move it to codebase/ as a repo ui reconcile command with tests, or record in the UI instructions that package-local maintenance scripts are allowed and what they may touch.

NextSTR-4

Define what prebuilt/ and enablers/ actually contain

prebuilt/.gitkeep · enablers/observability/README.md · pnpm-workspace.yaml

prebuilt/ is a workspace glob and a project type with no example and no manifest shape. enablers/ holds one README. Write a one-page contract for each: what a unit looks like, whether it has a project.json, which tasks it exposes, and one worked example. Container definitions and local compose are the natural first enabler content.

NextSTR-5

Split the web app into route groups before the second page

apps/web/app

There is one route. Authenticated and public surfaces will need different layouts, metadata, and guards. Introduce (public) and (app) route groups with the auth slice, so layout ownership is decided once rather than retrofitted.

On triggerSTR-6

Trim category directories that hold one file

servers/api/constants/{errors,http,runtime} · apps/web/types/{configuration,routing}

Eight constant files and five type files hold roughly twenty values between them, each behind a barrel. The categorization rule is sound at scale, but it currently adds navigation cost without separating anything.

Trigger: relax the rule to "categorize when a category passes three files", and apply it at the next policy revision.

Architecture

NowARC-1

Adopt a schema-first API contract

packages/validation · packages/types · servers/api features · apps/web/lib/api

Today request and response shapes are hand-written TypeScript in packages/types, with no runtime check on either side. Make zod schemas the source: request and response schemas live in packages/validation/<area>, types are inferred, the server validates input with them, and the web client parses responses with them. This is exactly the "infer the type from the shared schema" rule the standards already state.

Then choose one delivery style and record it. Plain REST with an OpenAPI document generated from the zod schemas keeps the API consumable by non-TypeScript clients. A typed RPC layer such as ts-rest or oRPC gives end-to-end inference with less code. Either is defensible; leaving it unchosen is not.

NowARC-2

Standardize the API conventions before the first business route

.agent/instructions · packages/types/src/errors

  • Versioning. Mount features under /v1; keep health unversioned.
  • Errors. Move the error envelope to RFC 9457 problem details, with a stable code extension the web app can switch on.
  • Collections. Fix cursor pagination, sorting, and filtering parameter names once.
  • Idempotency. Reserve an Idempotency-Key header for unsafe operations that clients may retry.
  • Time and identity. ISO 8601 UTC timestamps and opaque string ids in every contract.
NowARC-3

Pass a request context object explicitly

servers/api/middleware · feature service signatures

Request id, authenticated principal, and a request-scoped child logger will be needed by every feature. The repo forbids hidden global state, which rules out a bare AsyncLocalStorage singleton as the primary mechanism. Build a frozen RequestContext in middleware, attach it to res.locals, and pass it as the first argument to service functions. That keeps services pure with respect to Express and trivially testable.

NowARC-4

Complete the persistence boundary

servers/api/integrations/mongodb · features/*/<feature>.repository.ts

  • Repository contract. Repositories return plain frozen domain values, never Mongoose documents, so services never see the vendor.
  • Owned connection. Use a created connection passed as a dependency instead of the global default.
  • Schema change. Add a migration runner such as migrate-mongo, with migrations as a server task the control plane can order.
  • Indexes. Declare indexes in models, disable auto-indexing in production, and apply them in migrations.
  • Test database. Use mongodb-memory-server or Testcontainers for repository integration tests.
  • Transactions. Expose a withTransaction helper on the integration for multi-document writes.
NowARC-5

Decide how the web app talks to the API

apps/web/lib/api · decision record

Three patterns are available and the choice shapes auth, caching, and CORS:

  • Server-side calls only. Server Components and Server Actions call the API through a server-only client. The browser never sees the API origin. Simplest security model.
  • Backend for frontend. Next route handlers proxy to the API and own the session cookie. Good fit when the API should stay internal.
  • Direct browser calls. Needs CORS with credentials, CSRF protection, and a client cache such as TanStack Query.

Recommended default: server-side calls for reads and mutations, with direct browser calls added only where interactivity requires them.

NextARC-6

Add configuration layering and a secrets strategy

servers/api/config · apps/web/config · enablers

Both runtimes read flat environment variables with no notion of environment tiers. Record which values differ by environment, which are secrets, and where secrets come from in each tier. Add a control-plane check that every key in each validation schema appears in the matching .env.example.

NextARC-7

Close the loop between policy and tooling

architecture.yaml · codebase/validators

Publish a JSON Schema for architecture.yaml so editors and agents get validation and completion. Generate the import-boundary rules into ESLint rather than evaluating them with custom parsing, so violations surface in the editor while typing.

On triggerARC-8

Domain events and an outbox

When one feature must react to another's state change, publish domain events from services and persist them with the write in an outbox collection. That keeps features decoupled without introducing a broker early.

Trigger: the first cross-feature side effect, such as "send a welcome email when a user signs up".

On triggerARC-9

A worker runtime and a queue

servers/worker · servers/api/integrations/redis

BullMQ on Redis fits the stack and the functional model. The worker is a new server unit that shares feature services with the API through explicit dependencies, not through HTTP.

Trigger: the first operation that must not block a request, must retry, or must run on a schedule.

Product capabilities

Capabilities almost every product built on this foundation will need. None should be pre-built. Each should arrive as a feature slice when the product asks for it, using the conventions fixed above.

NowCAP-1

Authentication and sessions

Record the decision before writing code. Recommended default for this stack is an httpOnly, SameSite session cookie issued by the web tier, with server-side session storage, over bearer tokens in the browser. Better Auth is the current well-maintained option that supports Mongo and Next; Auth.js is the alternative. Cover sign-up, sign-in, sign-out, password reset, email verification, and session rotation in the first slice, and leave OAuth providers and MFA as follow-ups.

NowCAP-2

Forms bound to shared schemas

packages/ui compositions · apps/web/features

react-hook-form and its resolvers are already installed in the UI package. Add one generic form composition that takes a zod schema, renders field errors from the shadcn form primitive, and maps problem-detail validation errors from the API back onto fields.

NextCAP-3

Authorization

Start with roles on the user and a pure can(principal, action, resource) function per feature in <feature>.policy.ts. Enforce it in services, not only in routes, so the worker path is covered too. Move to attribute-based rules or a policy engine only when roles stop fitting.

NextCAP-4

Application shell and theming

The sidebar, breadcrumb, and navigation primitives are now in the UI package. Compose an authenticated shell in the (app) route group, wire next-themes with a full dark token set, and load fonts through next/font.

NextCAP-5

Rate limiting and audit trail

Rate-limit authentication endpoints from the first slice. Record security-relevant actions such as sign-in, role change, and data export in an append-only audit collection written by services.

Platform & operations

NowOPS-1

Local stack with one command

enablers/containers/compose.yaml · root dev script

The API requires MongoDB once the first feature persists anything. Add a compose file with MongoDB, and Redis only when it is needed. Have pnpm run dev start both runtimes with prefixed output after the database is healthy.

NextOPS-2

Container images for both runtimes

Multi-stage Dockerfiles using pnpm deploy to produce a pruned API image, and Next's output: "standalone" for the web image. Run as a non-root user, add a health check, and add them as image tasks so the control plane can order and cache them. That also gives the release profile's undefined artifact task a real meaning.

NextOPS-3

Environments, promotion, and the branch model

The remote has base, develop, stage, and main branches that no document explains. Write down which branch deploys where, how a change is promoted, and who approves production. Prefer trunk-based development with per-pull-request preview environments if the team is small.

NextOPS-4

Observability baseline

packages/telemetry · enablers/observability

  • Errors. Sentry or an equivalent in both runtimes, wired into error.tsx, a new global-error.tsx, and the API error handler.
  • Traces and metrics. OpenTelemetry SDK with HTTP, Express, and MongoDB instrumentation, exported over OTLP. The instrumentation code is a package; the collector and dashboards belong to the enabler.
  • Correlation. The request id from the request context in every log line and span.
  • Service levels. One availability and one latency objective per runtime, with alerts on burn rate.
NextOPS-5

Security baseline beyond scanning

  • Security headers and a Content Security Policy in the web app; helmet in the API.
  • Dependabot or Renovate for npm and GitHub Actions, with a release-age delay.
  • CodeQL or Semgrep on pull requests.
  • An SBOM generated in the release profile.
  • A secrets manager per environment, never plain CI variables for production.
  • A SECURITY.md with a disclosure route.
NextOPS-6

Operational runbooks and data safety

Document backup and restore for MongoDB and test a restore once. Write runbooks for the three incidents most likely early on: database unreachable, bad deploy, and leaked secret.

On triggerOPS-7

Infrastructure as code and remote cache

Add Terraform or Pulumi under an enabler when there is more than one environment to keep in sync. Add remote task-cache storage to the control plane when CI time, not correctness, becomes the bottleneck.

Developer experience

NowDX-1

A human README and onboarding path

Purpose, prerequisites, install, run, test, and where to read next, in under a page. Link to AGENTS.md for the rules rather than repeating them.

NowDX-2

A feature generator in the control plane

codebase/generators · repo generate feature

The strongest single lever for keeping the feature model consistent. repo generate feature api auth --roles route,service,repository writes only the requested role files, a test, and the router registration line, and the output passes repo check immediately. The existing project generator should be brought to the same standard.

NowDX-3

A doctor command

repo doctor checks the Node and pnpm versions, the managed TruffleHog binary, the presence of each .env against its example, database reachability, and line-ending configuration, and prints how to fix each. Today these failures surface only as confusing errors from later commands.

NextDX-4

Runner ergonomics

A --project filter, a watch mode for tests, prefixed streaming output, concurrency defaulting to available CPUs, and a timing summary at the end of every run.

NextDX-5

Test tooling that matches the testing standard

The standard describes component, integration, and end-to-end levels; the tooling supports only static rendering. Add vitest with jsdom and Testing Library for components, a database-backed integration harness for repositories, and Playwright for end-to-end journeys, with glob-based discovery in every unit.

NextDX-6

Component workbench for the UI package

Fifty-four primitives and three compositions with no place to see them. Storybook or Ladle in packages/ui, with an accessibility addon, gives reviewers and agents a visual contract and a home for visual regression later.

NextDX-7

Editor and commit hygiene

.editorconfig, .gitattributes, a formatter such as Prettier or Biome, recommended VS Code extensions and settings, commit message linting, and a pre-commit hook running the formatter and TruffleHog on staged files. Consider a dev container so Windows and Linux contributors share one toolchain.

Agent plane

The agent guidance is concise and consistent. Its gaps are about proof and repeatability rather than rules.

NowAGT-1

A feature playbook with a worked example

.agent/playbooks/add-feature.md

The instructions say what is allowed but never walk through adding a feature. Once the auth slice lands, write the steps against it: which files, in which order, which commands validate each step. Agents follow examples far more reliably than rules.

NowAGT-2

Decision records

.project/decisions/NNNN-title.md

Choices such as "no third-party orchestrator", "JSON-compatible YAML", "pnpm 11", and the coming auth and API-style decisions live only in prose and commit titles. A short record per decision with context, choice, and consequences stops later sessions from re-litigating them.

NowAGT-3

Evidence behind state claims

.project/PROJECT-STATE.md

The state document lists validations, including CI behaviour, that were not observed. Require each "Validated" line to cite a command and its result, or a CI run link, so the document stays a record rather than an intention.

NextAGT-4

Harness configuration committed to the repo

.claude/settings.json · .claude/skills

Allow-list the read-only repository CLI commands, add a hook that runs repo check after edits under codebase/, and package the feature playbook and the milestone record step as project skills so every session follows them the same way.

First vertical slice

M03.3 should be scoped to prove the conventions, not only to ship authentication. A slice that touches each layer once becomes the template every later feature copies.

Contract

  • Sign-up and sign-in schemas in packages/validation/auth
  • Inferred types, no parallel definitions
  • Problem-detail error codes for auth failures
  • Decision record for the session model

Server

  • features/auth with route, service, repository, model
  • Request context carrying the principal
  • Rate limit on the auth routes
  • First migration and index

Web

  • features/auth with forms bound to the shared schemas
  • (public) and (app) route groups with a guard
  • Server-only API client
  • Authenticated application shell

Proof

  • Service unit tests with fake repositories
  • Repository test against a real database
  • Form component test with Testing Library
  • One Playwright journey from sign-up to shell
  • A feature playbook written from the result

Deliberately not recommended

Things a generic enterprise checklist would suggest that would contradict this repository's principles or add cost without a current trigger.

  • A third-party monorepo orchestrator. The custom control plane is a deliberate choice; fix its cache and affected logic instead.
  • Microservices or a message broker now. One API and, later, one worker cover the foreseeable load. Split when a team or scaling boundary actually appears.
  • GraphQL. One first-party client and no aggregation need; a schema-first REST or RPC contract is cheaper.
  • A dependency-injection container or class-based services. Explicit dependency objects already give testability.
  • Empty scaffolding. No empty packages/validation, servers/worker, or role folders before their trigger.
  • Kubernetes as a first deploy target. A managed container platform is enough until there are several services to schedule.
  • Changesets or package publishing. Every package is private and consumed through the workspace protocol.

This review is forward-looking and does not repeat the defects in the companion audit. Fixing that audit's Critical items, especially the CI pipeline and the UI package build, comes before any recommendation here.
